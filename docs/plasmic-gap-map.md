# Plasmic Studio — mechanism-level gap map

Scoped 2026-08-13 against a live local bench (plasmicapp/plasmic @ shallow clone,
`platform/wab` running under podman at localhost:3003) plus a full source sweep.
This is the "break through to the next level" reference for the puck-studio fork:
how Plasmic actually builds each headline feature, what we already have that they
don't, and the recommended attack order.

All paths below are relative to `platform/wab` in the plasmic monorepo.
Stack: React 18 + MobX 6 + antd 4 + socket.io 4 + Slate + TypeORM.

## 0. The substrate everything sits on

- `shared/model/model-schema.ts` — a custom class-definition DSL compiled by
  `model-generator.ts` into `classes.ts`. Every studio object (Site, Component,
  TplNode, Variant, RuleSet, ArenaFrame…) is a generated class with a schema hash.
- `shared/core/observable-model.ts` — `observeModel()` deep-observes instances
  with MobX; `ChangeRecorder` captures a typed change log (path + before/after)
  for every mutation.
- All mutations flow through `studioCtx.change(...)`, which opens a recording
  window and dispatches the resulting changes to **four consumers: undo log,
  incremental CSS regen, save queue, multiplayer rebase**.

**Steal:** the change-log pipeline. Puck's plain-JSON model gives none of it free,
but ~80% is reachable with an immer `produceWithPatches` stream feeding the same
four consumers. This is the prerequisite for W5 undo, incremental CSS, and W6.

## 1. Breakpoints / screen variants (our W1)

Breakpoints are **not a separate concept** — one `GlobalVariantGroup` of type
`global-screen`; each breakpoint is a `Variant` with just a `mediaQuery` string
parsed to `{minWidth, maxWidth}`. Responsive strategy (mobile-first vs
desktop-first) is *inferred* from whether breakpoints use min- or max-width and
drives variant sort order → CSS cascade order. There is no viewport-switcher
widget: a Page Arena is a 2D matrix (columns = screen sizes, rows = variants) of
live artboards, all breakpoints visible side-by-side.

Files: `shared/Variants.ts:407-560`, `shared/responsiveness.ts`,
`shared/variant-sort.ts`, `client/components/sidebar-tabs/ResponsivenessPanel/`,
`client/components/studio/arenas/PageArenaLayout.tsx`.

**Steal:** breakpoints-as-variants = one cascade engine, not two. The device
preset table in `shared/responsiveness.ts` is copy-paste-able.

## 2. Component variants (our W3)

Every node carries `vsettings: [VariantSetting]`; each binds a variant combo to
a RuleSet + args/text/visibility. Base is just the combo `[baseVariant]`. Four
variant flavors in ONE class discriminated by fields: group variants (backed by
a state param, so variants are also props), standalone toggles, style/interaction
variants (`:hover`/`:focus`/… from a selector registry), code-component variants.
Resolution: collect vsettings whose combo is an ancestor of the active combo,
sort by an 8-tuple rank, merge in priority order (`effective-variant-setting.ts`).
Editing UX is a **pin model** (`PinManager.ts`): "target" (where edits record)
and "active" (what renders) are decoupled — preview hover while editing base.

**Steal:** the target-vs-active pin split; the single discriminated Variant class;
auto-generated artboard-per-variant grids (variant coverage as a visual matrix).

## 3. Style inspector

Data model: `RuleSet { values: Map[prop→cssString], mixins }` behind
`RuleSetHelpers`. Panel composition is data-driven: a `Section` enum + settings
table filtered by role permissions — section visibility is one table, not
scattered conditionals. The crown jewel is `DefinedIndicatorType`
(`shared/defined-indicator.ts`): every style prop classified as
`set / derived / otherVariants / mixin / theme / parentTplStyle / none`, rendered
as the colored dot beside each control with a popover explaining WHICH
variant/mixin/theme won and one-click unset/jump-to-source.

**Steal verbatim:** the DefinedIndicator union. Explaining *why* a value is what
it is costs one pure function over the style stack and is the single
highest-leverage inspector affordance.

## 4. Version history / undo (our W5)

Undo is log-based, not snapshot: `UndoRecord = { changes, viewState }` — undo
replays inverted changes AND restores focus/arena/selection. Three persistence
tiers: autosaved revisions (monotonic revisionNum, incremental deltas),
published PkgVersions (semver + tags), and real branches with a commit graph +
three-way model merge + conflict-picking UI (`shared/site-diffs/merge-core.ts`).
~250 numbered bundle migrations — the true cost of an evolving document schema.

**Steal:** record view state alongside model changes. Log-based undo is what
makes "undo one collaborator's change" tractable later.

## 5. Multiplayer (our W6)

**No CRDT, no OT.** socket.io rooms per project; two client events
(`subscribe`, `view`). Presence (cursors, selection boxes, follow-mode) is
ephemeral broadcast — cheap, high perceived value. Document sync is optimistic
local + server rebase at revision granularity: on conflict, undo local unsaved
changes → apply server bundle → replay yours → resolve (only tractable because
of the §0 change log). Fallback pessimistic mode: edit-lock banner + read-only.

**Steal:** presence-over-websockets decoupled from document sync. Presence is a
weekend; rebase is a quarter.

## 6. Page management (our W4)

A project holds a flat components map; a component IS a page iff it has
`PageMeta {path, params, title, …}` (dynamic routes supported). Navigation is by
**arenas**: PageArena/ComponentArena auto-derived per component (variant × screen
matrix), plus free-form mixed arenas. **Folders are fake** — parsed from `/` in
names (`folders-util.ts`); zero schema, zero migration, rename = move.

**Steal:** folders-as-name-prefixes; arenas as *views over components* rather
than a pages list.

## 7. Tokens / design system (our W2 — already partly shipped)

`StyleToken {uuid, name, value, type, variantedValues}` — token refs are stored
in rulesets as literal `var(--token-<uuid>)`, so a token reference IS a CSS
custom property; aliasing via ref-chain walk. `VariantedValue` gives a token a
different value per global-variant combo (= dark mode / theme-per-breakpoint)
using the same cascade engine as everything else. Mixins are named RuleSets;
Theme = default mixin + per-selector styles + `addItemPrefs` (per-element-type
default styles on insert). Token change → regenerate ONE `plasmic-vars`
stylesheet pushed into every artboard iframe: whole-canvas repaint, no re-render.

**Validation for us:** our BrandTokens + palette `var(--pN)` approach is the same
shape. **Steal:** varianted token values, `addItemPrefs`.

## 8. Canvas architecture — the big one

**One iframe per artboard.** Each ArenaFrame gets a sourceless iframe; loads are
serialized to avoid stampede. Inside renders the REAL user React tree using the
host app's React — user code components run for real, with tagged props mapping
DOM back to model nodes. Styles are real `<style>` tags injected per-frame,
regenerated incrementally per-component off the change log — so **media queries
evaluate natively against the iframe's own width**: a breakpoint artboard IS at
that breakpoint, not simulated. All editor chrome (selection boxes, margin/
padding drag handles, drop markers, measure tool) lives OUTSIDE the iframe in a
"scaler" coordinate space with zoom/scroll transforms. Spotlight mode dims
everything but the focused nested component via an overlay hole.

**Steal, in order:** (a) iframe-per-artboard with real injected CSS — the whole
ballgame for a responsive builder; (b) incremental per-component stylesheet
regen; (c) the scaler space so overlays stay crisp at any zoom.

## Cross-cutting polish worth copying

- **Shortcuts as data** — one table drives bindings AND the in-app cheat sheet.
  Figma-style single-key tools, `mod+k` command palette.
- **Command registry** — `{context, meta, execute}` objects expanded per
  available context, surfaced in the palette.
- **UiActionBus** (~100 lines) — any panel can "blink"/"jump to" any control by
  stable id, with a pending window for unmounted UI. How "click a warning → the
  control flashes" works.
- **Design linting** — `shared/linting/` flags e.g. breakpoint overrides that
  can't take effect. (We're AHEAD here: our rails lint blocks publishes
  server-side; theirs only annotates.)

## What we have that Plasmic doesn't

- **The rails**: publish-blocking brand lint (server-authoritative), two-lane
  brand/play severities, WCAG-measured token grades.
- **Brand cartridges**: swap-a-file re-theming of site AND editor chrome.
- **Number One**: our own AI copilot on our keys, rails-checked output.
- **Sovereignty**: CLI deploys, git-backed media, no cloud dependency; their
  studio is ~900k lines we'd never want to custody.

## Recommended attack order for puck-studio

1. **Change-log substrate** (§0) — immer `produceWithPatches` around Puck data;
   feeds undo, incremental CSS, and future multiplayer. Do first or pay 4×.
2. **Variant algebra + breakpoints** (§2+§1) — one engine; ~2,500 lines of pure,
   portable logic in Plasmic (`effective-variant-setting` + `variant-sort`).
3. **Iframe canvas + style manager** (§8) — biggest lift, biggest differentiator;
   makes breakpoints REAL instead of simulated.
4. **Inspector with DefinedIndicator** (§3) — mostly mechanical once variants
   exist.
5. **Varianted tokens** (§7) — cheap on top of our existing token rail.
6. **Presence multiplayer** (§5) — a weekend, high perceived value. Document
   rebase much later.
7. **Branches/merge** (§4) — defer; three-way model merge is ~2k lines.
